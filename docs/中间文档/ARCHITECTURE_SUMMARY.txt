ISSUE LIFECYCLE
===============

Creation:
  ┌─────────────────────────────────────────────────────────────────┐
  │ POST /api/issues                                                │
  │ {title, description, assignee_type?, assignee_id?, status?}     │
  └─────────────────────────────────────────────────────────────────┘
         ↓
  Issue created with default status: "backlog"
         ↓
  If assigned to agent & status != "backlog":
    → Enqueue task in agent_task_queue (status: queued)
    → Wake daemon with daemon:task_available event
    ↓
  Daemon claims task (POST /api/tasks/claim)
    ↓
  Daemon executes, streams progress (task:progress, task:message)
    ↓
  Daemon completes (POST /api/tasks/complete or /api/tasks/fail)
    ↓
  Server broadcasts (task:completed or task:failed)

Status Flow:
  backlog → todo → in_progress → in_review → done
                    (implicit on first exec)
                  ↓
                blocked (if task fails)
                  ↓
                cancelled (manual abort)


ASSIGNEE TYPES & TASK DISPATCH
===============================

member:
  • Human user assigned
  • No auto-execution
  • Notification-based (inbox, comments)

agent:
  • Autonomous LLM agent
  • Task auto-enqueued (if not in backlog)
  • Daemon claims & executes
  • Streams progress in real-time

squad:
  • Group of agents led by one leader
  • Squad leader's task enqueued
  • Leader orchestrates work among members


WEBSOCKET EVENTS
================

Issue Lifecycle:
  issue:created             → New issue added
  issue:updated             → Fields changed (with delta info)
  issue:deleted             → Issue removed
  issue_metadata:changed    → Pipeline state KV updated
  issue_reaction:*          → Emoji reactions
  issue_labels:changed      → Labels attached/removed

Task Lifecycle:
  task:queued               → ∅ → queued
  task:dispatch             → queued → dispatched (daemon claims)
  task:progress             → In-flight execution update
  task:message              → Tool calls, outputs
  task:completed            → running → completed (success)
  task:failed               → running → failed (error)
  task:cancelled            → * → cancelled (abort)

Agent Status:
  agent:status              → Connection state changed
  agent:created             → New agent added
  agent:archived/restored   → Lifecycle changes

Daemon Communication:
  daemon:heartbeat          → Daemon → Server (keep-alive ~30s)
  daemon:heartbeat_ack      → Server → Daemon (ack + pending work)

ISSUE METADATA (Pipeline State)
================================

Flat KV store for agents to record execution state without modifying
core issue fields. Always present (empty {} when unset).

Example:
  {
    "pr_number": "12345",
    "pr_url": "https://github.com/org/repo/pull/12345",
    "pipeline_status": "passed",
    "waiting_on": "code_review",
    "ci_run_id": "run-789",
    "commit_sha": "abc123"
  }

Constraints:
  • Flat structure only (no nested objects)
  • Primitive values only (string | number | boolean)
  • Updated via: PATCH /api/issues/{id}/metadata


KEY API HANDLERS
================

Issue CRUD:
  POST   /api/issues                    → Create
  GET    /api/issues/:id                → Read
  GET    /api/issues?...                → List (with filters)
  PATCH  /api/issues/:id                → Update
  PATCH  /api/issues?ids=...            → Batch update
  DELETE /api/issues/:id                → Delete

Agent Management:
  POST   /api/agents                    → Create
  GET    /api/agents/:id                → Read
  GET    /api/agents                    → List
  PATCH  /api/agents/:id                → Update
  GET    /api/agents/:id/tasks          → Get agent's tasks

Task Management (Daemon):
  POST   /api/tasks/claim?runtime_id=...     → Daemon claims next task
  POST   /api/tasks/{id}/start               → Daemon reports start
  POST   /api/tasks/{id}/complete            → Daemon reports success
  POST   /api/tasks/{id}/fail                → Daemon reports failure
  POST   /api/tasks/{id}/cancel              → Cancel a task

KEY DESIGN PRINCIPLES
====================

1. Task-Driven Execution:
   - Issues don't auto-execute; only when assigned to agent
   - "Backlog" is parking lot: stay there until explicitly moved
   - Enqueuing only happens when both assignee AND status conditions met

2. Isolation & Snapshots:
   - Task context snapshotted at creation (no fetch-on-demand)
   - Daemon has everything needed: issue state, env vars, instructions
   - Task can execute even if issue is deleted (context persists)

3. Flat Metadata for Pipeline State:
   - Agents record state in issue.metadata (not title/description)
   - Simple to search/filter by pipeline state
   - Survives issue deletion (snapshot in task.context)

4. Real-Time Synchronization:
   - All changes broadcast via WebSocket
   - Delta-based updates (what changed, not full object)
   - Clients merge updates into cache without refetch

5. Retry Support:
   - Tasks can link to parent_task_id (retry chain)
   - Attempt counter enables exponential backoff
   - Failure reason classifier aids debugging

6. Daemon Responsiveness:
   - Heartbeat every ~30s keeps agent status up-to-date
   - Task dispatch can be proactive (server → daemon)
   - No polling fallback for real-time task availability
